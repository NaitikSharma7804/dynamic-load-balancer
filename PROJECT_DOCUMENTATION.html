1. Project Statement & High-Level Overview

Statement: "We will build a system where multiple backend servers handle client requests through a central load balancer. The load balancer will distribute incoming traffic using algorithms like Round Robin, Weighted Round Robin, and Least Connections. A health monitoring system will continuously check whether each server is available, and if a server goes down, the load balancer will automatically stop sending requests to it and redirect traffic to healthy servers. We can also demonstrate server failure/recovery, response time, traffic distribution, and network packets using Wireshark."

Dual-Port Concurrency

Runs the high-speed Reverse Proxy on Port 8080 and the administrative control plane on Port 9090 simultaneously on an async loop.

Zero-Downtime Reconfiguration

Switch algorithms (Round Robin → Least Connections) or drain/add servers at runtime via the Admin API without restarting the proxy.

Active Heartbeat & Auto-Failover

Background probes ping GET /health every 2s. If a server misses 3 checks, it is isolated instantly with zero dropped requests.

Real-time Dashboard & Benchmark

Live glassmorphism web control panel with Chart.js visualization, plus an async benchmark tool logging P50, P95, and P99 latencies.

3. The 4 Load Balancing Algorithms Detailed

1. Round Robin (round_robin.py)

Evenly cycles requests through the list of healthy backends in fixed rotational order: b1 → b2 → b3 → b1 → b2 → b3. Best when all backend servers have identical CPU/memory specs and predictable response times.

2. Smooth Weighted Round Robin (weighted_rr.py)

The mathematical algorithm utilized by Nginx. Rather than sending 5 requests in a row to b1 (which causes server queue spikes), it smoothly interleaves selections based on configured weights (5 : 3 : 1): b1 → b2 → b1 → b3 → b1 → b2 → b1 → b2 → b1. Prevents queue saturation on high-capacity nodes while still distributing 5x more work to b1.

3. Least Connections (least_conn.py)

Inspects the active_connections counter of each healthy node in real time. Routes incoming traffic to the backend currently processing the fewest active concurrent requests. In our cluster:

  • b1 finishes requests in 50ms (releases connection quickly).
  • b3 takes 200ms (holds connection 4x longer).
  • Under concurrent load, Least Connections naturally pushes more traffic to the faster server (b1), maximizing overall cluster throughput!

4. IP Hash (ip_hash.py)

Computes hash(client_ip) % len(healthy_backends). Guarantees session stickiness: requests from the same user or machine consistently land on the exact same backend, preserving in-memory sessions without external Redis caches.

4. Active Health Monitoring & Automatic Failover

The State Machine

  • Probe Frequency: Every 2.0 seconds, the background health task issues an async GET http://<host>:<port>/health request with a 1.0s timeout.
  • Failure Detection (3 Strikes):
    • 1st failure: Backend marked SUSPECT.
    • 3rd consecutive failure: Backend marked UNHEALTHY and instantly evicted from active routing.
  • Zero Dropped Requests: If a backend crashes right during a request, the proxy catches the network error and automatically retries an alternate healthy backend (up to retry_count = 1).
  • Automatic Recovery: When the crashed server restarts, it must pass 2 consecutive health checks before re-entering the cluster.
  • Slow-Start Ramp-Up: Once recovered, its effective weight scales up gradually over 10 seconds (slow_start_s = 10) to prevent cold caches from being overwhelmed.
  • Audit Logging: All transitions (failures, recoveries, drains, undrains, algorithm changes) are logged in memory and served at GET /admin/health.

Top 5 Faculty Viva Questions & Answers:

Q1: Why is this a Layer 7 load balancer instead of Layer 4?
Answer: Layer 4 load balancers only inspect IP addresses and TCP port numbers without looking at payload. Our system operates at Layer 7 (Application Layer): it parses HTTP paths (/{path:path}), HTTP headers (injects X-Served-By), evaluates client IP hashes, and checks application health endpoints (/health).

Q2: How does your health monitor avoid false positives?
Answer: It implements a consecutive failure threshold (unhealthy_threshold = 3). A single temporary network blip only marks the server as SUSPECT; 3 consecutive failed probes are required before evicting it. For recovery, it requires 2 consecutive successful checks (healthy_threshold = 2) followed by a 10s slow-start warmup.

Q3: How does Least Connections work in asynchronous Python?
Answer: Each backend object maintains an active_connections counter protected by an asyncio.Lock. When a request is forwarded, the lock is acquired and counter incremented; when the response streams back, the counter is decremented. The algorithm inspects this counter in real time to route to the least-burdened server.

Q4: What makes Smooth Weighted Round Robin better than simple Weighted Round Robin?
Answer: Simple Weighted Round Robin sends bursts of 5 consecutive requests to the heaviest node before touching others. Smooth Weighted Round Robin (the Nginx algorithm) continuously recalculates current weights and smoothly interleaves servers (e.g. b1, b2, b1, b3, b1), preventing high-weight server queue spikes.

Q5: What happens if a backend fails mid-request?
Answer: The Proxy Engine wraps the forwarding call in an exception block. If a backend fails or times out, the proxy isolates the failure, acquires an alternate healthy backend from the pool, and retries the request up to retry_count = 1, ensuring zero 502/504 errors for clients.
